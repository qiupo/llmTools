# MiniCPM4.1-8B 与 Qwen3.5-9B 全面替代评估

日期：2026-07-30

## 结论

**`MiniCPM4.1-8B-MLX` 当前不能全面替代 `Qwen3.5-9B-MLX-4bit`，也不应成为 llmTools 的优先推荐质量模型。**

MiniCPM4.1-8B 的 MLX 兼容性、冷启动、常驻内存和普通文本速度都不错，但它在 llmTools 现有严格结构化协议上出现了稳定、可复现的失败：

- 桌面助手资格连续两轮均为 `JSON 0/24`，无法进入可用模型集合。
- 即使离线宽松去除 Markdown 围栏和反斜杠，仍有 `7/12` 个负例被误判为应主动打扰，远超允许的 `1/12`。
- 详细翻译连续两轮没有通过结构化契约。
- 5,698 字、2 分块的会议纪要虽然生成了可读文字，但决策、待办、开放问题和主题数组全部为空。
- TTS 角色分析连续两轮返回转义后的 JSON，产品解析器得到 `0` 个角色片段。
- MiniCPM4.1-8B 是纯文本模型，不能覆盖当前 Qwen3.5-9B 已登记的图片输入能力。

因此本轮不修改推荐模型、不修改默认路由，也不为了 MiniCPM 放宽结构化解析器。`Qwen3.5-9B-MLX-4bit` 继续承担质量文本、会议纪要和需要严格结构化输出的本地任务。

## 评估对象与真实职责

当前实时注册表中，Qwen3.5-9B 的实际职责不是单一聊天模型：

- 润色、摘要、解释、待办四项文本功能都把它设为任务默认模型。
- 会议纪要模型明确选择 Qwen3.5-9B。
- TTS 角色分析默认复用本地会议纪要文本模型。
- 桌面助手判断模型未手工固定时，会从已通过资格的本地质量模型中自动选择。
- 注册表把 Qwen3.5-9B 标记为支持 `text + image`；MiniCPM4.1-8B 只支持文本。

网页翻译当前使用 `MiniCPM5-1B-MLX`，不是本次 9B 替代范围，因此没有把网页批量翻译作为决定性门槛。

## 替代门槛

门槛在运行 MiniCPM 前确定，避免根据结果倒推标准：

1. 当前 Swift/MLX 路径可直接加载，不依赖远程 provider 或单独 Python runtime。
2. 六项现有文本夹具全部完成，关键事实不能明显丢失或虚构。
3. 详细翻译必须产生可解析的译文、备选译法和 3 至 8 个原文术语。
4. 桌面助手必须满足现有资格门槛：`JSON 24/24`、正例至少 `9/12`、P06 至少 `3/4`、负例误报至多 `1/12`、硬负例 `0`、最大热延迟不超过 `5000ms`。
5. 长会议纪要必须经过至少 2 个分块并正确恢复摘要、决策、待办、开放问题和主题。
6. TTS 角色分析必须覆盖全部源片段，并产生可解析的角色、旁白/对白类型、表达方式和停顿。
7. `unloadAll()` 后 runner 必须解除模型占用。
8. 在正确性门槛全部满足后，磁盘、内存或延迟至少有一项形成明确收益。

## 测试设计

每个模型执行两轮完全相同的最终套件。每轮包含：

- 一次冷加载和模型生命周期检查。
- 6 个普通文本任务：英译中、中译英、中文润色、中文摘要、中文技术解释、待办提取。
- 1 个详细翻译结构化任务。
- 1 次助手预热和 24 个冻结资格夹具。
- 55 段、5,698 字的长会议纪要；产品分块阈值为 5,000 字，因此固定触发 2 个分块和最终合并。
- 89 字、7 个源片段的中文有声文案角色分析。
- `unloadAll()` 前后 runner 状态检查。

原始输出和 `/usr/bin/time -l` 日志保存在：

- `dist/benchmarks/model-replacement-2026-07-30/qwen3.5-9b.json`
- `dist/benchmarks/model-replacement-2026-07-30/qwen3.5-9b-run3.json`
- `dist/benchmarks/model-replacement-2026-07-30/minicpm4.1-8b.json`
- `dist/benchmarks/model-replacement-2026-07-30/minicpm4.1-8b-run2.json`
- 同目录下对应的 `.log` 文件。

## 性能与资源

以下数字取两轮最终套件的范围；平均节省比例只用于描述本机结果。

| 指标 | Qwen3.5-9B | MiniCPM4.1-8B | MiniCPM 变化 |
| --- | ---: | ---: | ---: |
| 目录占用 | 5.57 GiB | 4.30 GiB | -22.8% |
| 冷加载 | 1484-1486ms | 457-565ms | 平均 -65.6% |
| 最大 resident set | 约 5.83 GiB | 约 4.44 GiB | 平均 -23.9% |
| `time -l` peak footprint | 约 49.40 GiB | 约 14.31 GiB | 平均 -71.0% |
| 六项文本总耗时 | 7324-9643ms | 5893-6928ms | 平均 -24.4% |
| 详细翻译 | 18223-25170ms，通过 | 15834-18243ms，失败 | 不构成等价收益 |
| 助手单项最大热延迟 | 4336-5196ms | 3044-3382ms，输出非法 | 不构成等价收益 |
| 长会议纪要 | 24789-30008ms，通过 | 17150-18193ms，结构失败 | 不构成等价收益 |
| TTS 角色分析 | 13616-15759ms，通过 | 8905-9572ms，解析失败 | 不构成等价收益 |
| 全套墙钟时间 | 144.38-174.38s | 115.42-129.16s | 平均 -23.3% |

`maximum resident set size` 是进程 CPU 侧常驻高水位；`peak memory footprint` 还会反映本机 MLX/Metal 统一内存分配高水位。后者不等于卸载后的稳态 RSS，但对同一二进制、同一测试序列仍有比较意义。MiniCPM 的资源优势是真实且明显的，只是它完成的是“生成了响应”，不是“成功完成了所有产品契约”，所以不能单独据此提升推荐级别。

## 普通文本质量

两轮 `temperature=0` 输出稳定。人工按事实完整性、语言自然度和指令遵循逐项检查：

| 任务 | Qwen3.5-9B | MiniCPM4.1-8B | 判断 |
| --- | --- | --- | --- |
| 英译中 | “该版本会保留……”自然、准确 | “该发布保留……”略生硬 | Qwen 更好 |
| 中译英 | 准确保留“先原文、后译文、本地完成、不上传音频” | 语义完整，但 `completes its task` 和 `uploads are not allowed` 稍生硬 | Qwen 略好 |
| 中文润色 | “首次启动时加载速度可能稍慢，请您稍候片刻再试”更像产品文案 | “用户稍等片刻后再尝试”语气与主语不够自然 | Qwen 更好 |
| 中文摘要 | 三点完整保留实时/文件分流、本地处理和新会话生效 | 保留事实，但额外虚构“实施分离、优化策略”两个行动项 | Qwen 明显更好 |
| 技术解释 | 三句话但先复述“这段文本是一个指令”，不够直接 | 直接解释上下文连续性，严格三句话 | MiniCPM 更好 |
| 待办提取 | 四个任务正确，但额外输出负责人/日期/优先级字段 | 简洁、准确拆成四项 | MiniCPM 更好 |

普通文本层面不是单方面碾压：Qwen 在产品文案、事实保真和摘要上更稳；MiniCPM 在短技术解释和简洁待办上更好。按本组固定夹具，Qwen 占优 4 项，MiniCPM 占优 2 项。

## 详细翻译失败

Qwen 两轮都返回可直接解析的 JSON，包含 3 个备选译法和 7 个来自英文原文的术语。

MiniCPM 两轮都出现同一失败模式：

1. 把整个 JSON 对象输出成带字面量 `\\n` 和 `\\"` 的转义文本。
2. `keyTerms.term` 返回“浏览器扩展程序、链接、表单字段、新用户”等中文译文，而契约要求术语必须存在于英文源文。
3. 部分音标和词性字段不可信，例如混合拼音、英文和转义字符。
4. `TaskEngine` 因结构化解析失败而回退为普通译文，所以用户能看到译文，但看不到可信的详细学习信息。

这不是只去掉反斜杠就能修复的问题：术语方向和字段内容本身也不符合契约。

## 桌面助手资格失败

严格产品解析结果在两轮中完全一致：

| 指标 | Qwen3.5-9B | MiniCPM4.1-8B |
| --- | ---: | ---: |
| 合法 JSON | 24/24 | 0/24 |
| 正例通过 | 11/12 | 0/12（严格解析） |
| P06 正例 | 4/4 | 0/4（严格解析） |
| 负例误报 | 1/12 | 0/12（因为全部先解析失败） |
| 硬负例 | 0 | 0 |
| 最大热延迟 | 4336ms / 5196ms | 3382ms / 3044ms |
| 最终状态 | qualified / unqualified（仅超时） | unqualified / unqualified |

为了判断是否只是格式问题，另做了不进入产品代码的离线宽松解码：去除 Markdown 围栏，把字面量 `\\n`、`\\"` 恢复后尝试普通 `JSON.parse`。MiniCPM 两轮结果均为：

- 23/24 可以被宽松 JSON 解析；`p01-build` 仍是语法损坏。
- 11/12 正例会主动展示。
- 7/12 负例也会主动展示。

误报的负例包括：普通全屏视频、教程中的预期错误、互不相关的外语剪贴板、普通代码/URL、输入中的未完成草稿、被动观看培训视频、普通被动阅读。部分输出还使用了不存在的 action ID 或 task 值。

因此不能通过放宽 `AssistantJudgmentContract.parse` 解决。这样做既会削弱现有安全边界，也仍然无法通过语义资格门槛。

Qwen 的残余问题也需要记录：两轮语义结果完全一致，但其中一轮最大延迟 `5196ms`，比 5 秒门槛多 `196ms`；空闲复测恢复到 `4336ms`。这说明 Qwen 当前在 M5 Pro 上接近延迟门槛，应单独关注热延迟余量，但它不是把一个结构化和语义均失败的模型提升为默认的理由。

## 长会议纪要

会议夹具包含明确的替代条件、发布日期、三项负责人待办和一个 16GB 设备开放问题，并故意超过 5,000 字分块阈值。

Qwen 两轮均：

- `chunkCount=2`。
- 返回独立摘要。
- 正确提取替代门槛、测试环境、网页翻译继续使用 MiniCPM5、八月八日发布条件等决策。
- 正确提取陈宁、周然、林夏三项待办。
- 正确保留 16GB Mac 稳定性开放问题。

MiniCPM 两轮虽然也完成 2 分块并抓住主要语义，但最终 Markdown 同样以字面量转义形式返回。现有解析结果为：

- `summary` 包含整篇伪 Markdown。
- `decisions=[]`。
- `actionItems=[]`。
- `openQuestions=[]`。
- `topics=[]`。

界面能够显示一段文字不等于会议纪要功能通过；结构化栏目、后续导出和状态判断都会退化。

## TTS 角色分析

Qwen 两轮均得到：

- 3 个音色：旁白、林夏、周然。
- 7 个源片段全部覆盖。
- 旁白、对白、动作描写、表达方式和停顿均可解析。

MiniCPM 两轮均报：`角色识别失败：本地模型没有返回完整的 JSON。`

第二轮显式记录的原始响应表明，角色和 assignments 外形基本存在，但整个对象仍被输出成 `\\"` 转义文本；同时若干动作描写被标成 dialogue。即使增加通用反转义，仍需继续修复类型判断，不能视为可直接替代。

## 模型接入与能力边界

MiniCPM 的基础接入没有发现参数遗漏：

- `model_type=minicpm` 已由当前 `mlx-swift-lm` loader 支持。
- 官方 chat template 在 `enable_thinking=false` 时会插入空 think 区段。
- `MLXRunner` 已把 `enable_thinking` 传给 chat template。
- 助手资格显式关闭 thinking，所有结构化任务使用 `temperature=0`。
- 两轮都能稳定加载、持续生成并卸载，没有 Metal 崩溃。

当前还有两个非阻断但需要记录的集成差异：

1. `ModelDetection.inferSizeClass` 没有 `8b` token，因此 MiniCPM 被识别为 `sizeClass=custom`、`role=default`，不会自动进入质量模型优先级。
2. 当前 Swift MiniCPM 实现走普通 scaled dot-product attention；官方 CUDA/InfLLM 稀疏推理加速数字不能直接套用到 llmTools。本文只使用本机实测速度。

由于结构化和语义门槛已经失败，本轮没有为 `8b` 元数据增加特殊规则，也没有新增 MiniCPM 专用输出修补分支。

## 产品决策

本轮建议保持：

- `Qwen3.5-9B-MLX-4bit`：继续作为质量文本、会议纪要、TTS 角色分析和桌面助手资格候选。
- `MiniCPM5-1B-MLX`：继续承担网页翻译和低延迟普通文本角色。
- `MiniCPM4.1-8B-MLX`：仅保留为本地实验模型，不加入优先推荐，不切换任何默认路由。

MiniCPM4.1-8B 可以用于用户手工选择的普通解释、待办和其他不依赖结构化协议的文本任务，但这个位置已经与 MiniCPM5-1B、Qwen3.5-0.8B 重叠，当前没有足够产品收益值得增加默认推荐复杂度。

## 重新评估条件

只有出现新的官方权重、针对严格结构化输出的微调版本，或明确的模型专用 prompt 改进后，才值得重新测试。重新提升为推荐模型至少需要：

1. 连续两轮原生返回 `24/24` 严格合法助手 JSON，不依赖通用反转义容错。
2. 连续两轮负例误报不超过 `1/12`，P06 至少 `3/4`，硬负例为 `0`。
3. 详细翻译、2 分块会议纪要、TTS 角色分析连续两轮全部通过。
4. 普通摘要不虚构行动项。
5. 明确接受“文本模型 + 独立视觉模型”的双模型路由，或使用具备图片输入的对应模型。
6. 在 16GB/24GB Apple Silicon 上补做内存压力和长会话稳定性测试。

## 限制

- 本次只在一台 64GB M5 Pro 上运行，不能证明 16GB 机器可用。
- 六项普通文本夹具样本较小，人工判断不是通用排行榜。
- 没有测试图片输入，因为 MiniCPM4.1-8B 本身是纯文本模型；能力缺失已直接计入全面替代结论。
- 没有单独测量能耗、电池续航或并发请求。
- `time -l` 的 peak footprint 是整个多任务进程的高水位，不代表单次短请求稳态内存。
